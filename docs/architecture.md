## 1. テクノロジースタック

### 1-1. 全体方針

- 利用者約120名・3機能+周辺機能限定という小〜中規模要件のため、**大規模インフラは不要**。運用・保守コストを最小化できるシンプルな構成を優先する(確信度: 高、要件定義書2章・6章の方針を踏襲)。
- ファイル実体は自社所有のオンプレミスWebサーバーのローカルディスクに保存する方針(要件定義書6-1章で確定済み)のため、**オンプレミス(または自社管理サーバー)を前提とした構成**とする。
- 開発・保守をアルゴのエンジニアチームが兼務する想定のため、**チームが使い慣れた技術を優先**し、学習コストの高い技術は避ける(要確認: 既存の知見があるクラウド事業者・言語・フレームワーク)。

### 1-2. 提案スタック

| レイヤー | 技術(提案) | 理由 |
|---|---|---|
| フロントエンド | React + TypeScript、Tailwind CSS | CLAUDE.md規約でTailwind CSS採用を規定。モックアップ(`docs/mockups/*.html`)のデザイントークン(角丸カード・罫線テーブル・カラーパレット)をコンポーネント化しやすい |
| バックエンド | Node.js(TypeScript)+ 軽量Webフレームワーク(例: Fastify/Express相当) | フロントと言語統一によりチームの学習コスト・保守コストを下げる。120名規模の同時アクセスには十分な性能 |
| DB | SQL Server(社内オンプレミス、ホスト: 10.194.5.57)**確定** | 構造化データ(投稿・予定・利用者・ファイルメタデータ等)を一元管理。ER図(`functional-design.md`)はRDBMSを前提に設計しており、SQL Serverでもそのまま適用可能 |
| DBアクセス方式 | 素のドライバ(`mssql`/tedious)を直接使用、**確定(2026-08-27)** | ORMを介さず直接SQLを記述する方針。自由度を優先し、スキーマ定義・マイグレーション・型定義は自前で用意する |
| ファイルストレージ | オンプレミスWebサーバーのローカルディスク(ファイル実体)+ DBにメタデータ | 要件定義書6-1章のB案を踏襲。実体をDBにBLOB格納しない |
| 認証 | 独自ID/パスワード認証(セッションベース or JWT)、パスワードはハッシュ化(bcrypt等)して保存 | SSO連携不要と確認済み。パスワード再表示不可設計(要件3-7) |
| 外部API連携 | Google Calendar API(OAuth 2.0、Webhook通知) | 個人オプトインの双方向同期(要件3-1、C案) |
| リッチテキスト処理 | サニタイズ用ライブラリ(例: DOMPurify相当のサーバーサイド実装) | 掲示板本文のXSS対策を必須要件とする(要件3-5) |
| バックアップ | DB・ファイル実体の日次バックアップを、本体サーバーと物理的に別の場所(別ディスク・社外・クラウドストレージ等)へ保存 | オンプレミス構成の単一障害点(SPOF)対策(要件6-1章・8章) |

**確定事項(2026-08-27)**: DBは社内既存のSQL Server(10.194.5.57)を利用する。新規にDBサーバーを構築せず、既存インフラを再利用する構成となる。DBアクセスはORMを介さず`mssql`(tedious)ドライバを直接使用する。マイグレーションはバージョン管理されたSQLスクリプト(`backend/src/db/migrations/`に採番して配置)で管理する。

**未確定・要確認**: アルゴのエンジニアチームが既に使い慣れているクラウド事業者(AWS/GCP/Azure等)の有無、具体的な言語・フレームワークの経験。既存知見があれば上記提案より優先する。

### 1-3. 本番デプロイ構成(Windows Server + IIS)**確定(2026-08-27)**

本番環境は自社所有のWindows Server上のIISで稼働させる。IISはNode.jsアプリケーションを直接実行できないため、以下の構成とする。

| 要素 | 構成 |
|---|---|
| フロントエンド(静的ファイル) | Reactの本番ビルド成果物(`frontend/dist/`)をIISが直接配信する静的サイトとして配置。SPAのクライアントサイドルーティングに対応するため、存在しないパスへのリクエストを`index.html`にフォールバックさせるURL Rewriteルールを`web.config`に設定する |
| バックエンド(API) | Node.jsプロセスをOS上に常駐させ、内部ポート(例: `localhost:3001`)でのみ待ち受けさせる。外部には直接公開しない |
| IISの役割 | **リバースプロキシ(ARR: Application Request Routing)**として動作。`/api/*`宛のリクエストをURL Rewrite + ARRで内部のNode.jsプロセスへ転送する。HTTPS終端(証明書バインド)はIIS側で行う |
| Node.jsプロセスの常駐化 | IISのプロセスライフサイクル(アプリケーションプールのリサイクル等)には乗らないため、**Windowsサービスとして常駐**させる(例: `node-windows`、PM2のWindowsサービス化、NSSM等)。サーバー再起動時の自動起動、クラッシュ時の自動再起動を設定する |
| ファイル共有の実体 | 本番運用でもこのWindows Server上のローカルディスクに保存する(要件定義書6-1章の方針をそのまま踏襲) |

**前提条件**: 対象のWindows ServerにIISのARRモジュール・URL Rewriteモジュールがインストールされていること(未確認、要事前準備)。

## 3. 技術的制約と要件

- **SSO不要**: Google Workspace/Microsoft 365等の既存認証基盤との連携は行わない。独自ログインのみ。
- **社員のGoogleアカウントの多様性**: 大半が個人Gmailアカウントのため、Google Workspace管理者権限に依存した一括制御(強制アクセス取消等)はできない。退職時の同期解除はアプリ側でrevoke APIを呼び出す設計とする(要件3-1・3-7)。
- **Google OAuthアプリ審査**: 機密性の高いスコープを要求する場合、審査に数日〜数週間を要する可能性がある。開発スケジュールに審査期間を織り込む必要がある(要件3-1・9章)。
- **Webhook購読の期限**: Google Calendar APIのpush通知はおおむね1週間で失効するため、定期的な再購読処理が必要(要件3-1)。
- **オンプレミス特有の制約**: 物理サーバー1台構成は単一障害点(SPOF)になる。バックアップは物理的に別の場所に保存する必要がある(要件6-1・8章)。将来的な複数台構成(冗長化)の予定有無は未確認。
- **既存SQL Server(10.194.5.57)への接続**: Webアプリケーションサーバーから当該DBホストへのネットワーク到達性・ファイアウォール許可(ポート開放)が前提となる。接続文字列・認証情報はソースコードに直書きせず、環境変数(`.env`等、`.gitignore`対象)で管理する。既存DBサーバーを他システムと共用する場合、本プロジェクト専用のデータベース/スキーマを分離して作成することを推奨する。DBサーバー自体のバックアップ運用が既存の全社ルールに従うのか、本プロジェクト側で個別に日次バックアップを追加する必要があるのかは要確認。
- **祝日データ**: 内閣府公表データまたはGoogleの「日本の祝日」カレンダー等の外部データを取り込む方式を想定。自動取込みにしても年1回の目視確認が必要(要件3-2)。
- **セキュリティ**: 通信はHTTPS必須。掲示板本文はHTMLとして保存されるためサニタイズ必須(XSS対策)。パスワードは平文保存禁止・ハッシュ化必須。個人情報(氏名・所属・連絡先等)を扱うため、個人情報保護法上の安全管理措置を専門家に確認することを推奨(要件8章)。
- **ゴミ箱機能なし**: ファイル共有・掲示板ともゴミ箱機能を持たないため、誤削除時の実質的な復旧手段は日次バックアップからの復元(1日単位の粒度)のみ。操作ログが唯一の追跡手段となる(要件3-4・3-6)。
- **IIS(ARR)によるリバースプロキシ構成**: IISはリクエストの受付・HTTPS終端・静的ファイル配信・`/api/*`のリバースプロキシに専念し、Node.jsプロセスの起動・監視はIISの外側(Windowsサービス)で行う。IIS側のアプリケーションプールのアイドルタイムアウト設定がNode.jsプロセスには影響しないことを前提とする(Node.js側はIISとは独立したライフサイクルで常駐する)。
- **Node.jsの稼働監視**: IISのようにクラッシュ時の自動復旧機構を標準で持たないため、Windowsサービス化の際にクラッシュ時の自動再起動・ログ出力先の設定を行う。
- **サーバーのタイムゾーン(重要)**: 会議候補日時の自動抽出(要件3-10)の営業時間判定(平日9:00〜17:30)は、アプリケーションサーバーの**ローカル時刻**を基準に計算する設計とした(UTCとの固定オフセット計算ではない)。そのため**本番Windows Serverのタイムゾーンを日本標準時(JST)に設定する必要がある**。UTC等の別タイムゾーンで運用すると、営業時間判定・カレンダー表示がすべてずれる。

## 4. パフォーマンス要件

| 項目 | 要件(案) |
|---|---|
| 同時アクセス | 120名程度が安定して同時利用できること。サイボウズOffice比で過剰なインフラは不要(小〜中規模構成で十分、要件定義書5章) |
| 応答時間 | 一般的な画面遷移・一覧表示は体感で数百ms〜1秒程度を目標(具体的な数値目標は基本設計フェーズで確定) |
| 会議候補日時の自動抽出 | 複数人・最大2週間分のfree/busy計算を、UI上で待機が気にならない時間内(数秒以内目安)で返す設計とする |
| 可用性 | 業務時間帯の安定稼働を確保。バックアップはRPO(目標復旧時点)1日(日次バックアップ前提) |
| データ移行 | 現行サイボウズOfficeからの移行データ量(全件 or 直近分)によって移行処理時間が変動するため、範囲確定後に見積もる |
