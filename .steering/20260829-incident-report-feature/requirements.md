# 事故報告機能 要求定義

作成日: 2026-08-29
参照元: `reference/20260826（津野）事故報告書(WEB班）.xls`(社内で実際に使われているオペレーション事故報告書)
ステータス: ドラフト(要確認・要承認。xlsはバイナリ形式のため文字列抽出による推測を含む)

---

## 1. 背景・目的

現在、社内でオペレーション事故(誤出荷・誤対応等)が発生した際、Excelファイル(`事故報告書`)に手入力して記録・共有している。これをグループウェアの機能として追加し、報告・確認・周知のフローをシステム化する。

**注記**: 本機能は当初の要件定義書(`casemax_groupware_requirements.md`)のスコープには含まれていない追加機能である。同ドキュメントの方針(「スコープ肥大化を避け、追加要望は都度必要性を検討する」)に照らし、独立した機能追加として本ステアリングディレクトリで要求・設計・タスクを管理する。

## 2. 参照元ファイルから読み取れた項目(暫定)

元のxlsファイルはバイナリ形式であり、Excel COM経由の変換が本セッションでは安定動作しなかったため、バイナリ文字列抽出で読み取れた範囲の項目を暫定的に整理する。**フォント名・スタイル名等のノイズを除外した業務項目と思われるもの**は以下の通り。

| 項目(読み取れた文言) | 想定される内容 |
|---|---|
| 事故報告書(表題) | 帳票タイトル |
| 発生日時 | 事故が発生した日時 |
| 得意先コード | 取引先を特定するコード |
| 商品名 / 該当商品 | 事故に関連する商品 |
| お客様情報 | 顧客の情報(氏名・連絡先等と推測) |
| 事故内容 | 何が起きたかの説明 |
| 対処状況 | 事故発生後にどう対応したか |
| 具体的実施内容 | 対応の詳細 |
| 説明文 | 自由記述の説明(定型文＋自由入力と推測) |
| 担当営業 | 事故に関連する営業担当者 |
| チェック者 | 内容を確認した人 |
| 周知担当者・日時 | 社内周知を行った担当者・日時 |
| 返却倉庫名 | 返品・返送に関連する倉庫 |
| 事故区分(例: 送り先間違い) | 事故の分類(選択式と推測) |

**未確認**: 上記は文字列の断片からの推測であり、正確な項目名・入力形式(自由記述/選択式/必須任意)・項目間のレイアウト構造は確認できていない。実際の帳票を画面共有等で確認いただくか、項目一覧を教えていただくことを推奨する。

## 3. ユーザーストーリー(たたき台)

- **事務員として**、オペレーション事故が発生した際に、この画面から発生日時・得意先・事故内容・対処状況・担当営業を入力して報告したい(要件確定: 基本的に事務員が入力する)。
- **営業として**、自分が担当する得意先に関する事故報告を、発生時に知らされていなくても後から一覧で絞り込んで確認したい(要件確定2026-08-29: 事故は営業の知らないところで発生することがあるため、担当営業による絞り込み機能が必須)。
- チェック者として、提出された事故報告の内容を確認し、承認や差し戻しを行いたい。
- 周知担当者として、事故報告が確定した後、関係者へ周知した日時を記録したい。
- 管理者として、過去の事故報告を検索・一覧できるようにしたい(再発防止・傾向分析のため)。

## 4. 受け入れ条件(たたき台)

- 事故報告書の主要項目(発生日時、得意先コード、商品名、事故内容、対処状況、具体的実施内容、担当営業)を入力し、保存できる。
- **一覧画面で「担当営業」による絞り込み検索ができる**(確定2026-08-29。営業担当が自分に関連する事故報告を後から確認できるようにするため)。担当営業はプルダウン等で既存の利用者(app_user)から選択する形を想定。
- チェック者による確認状態(未確認/確認済み等)を記録できる。
- 周知担当者・周知日時を記録できる。
- 一覧画面で過去の事故報告を検索・参照できる。
- お客様情報など個人情報を含む項目は、既存のファイル共有(3-4章、アクセス権限なし)とは異なる扱いが必要か検討する(下記5章参照)。

## 5. 論点・確認事項

- **アクセス権限(閲覧)**: **確定(2026-08-29)**。全社員が閲覧可能とする(既存の掲示板・ファイル共有と同様、閲覧に権限制御は設けない)。
- **アクセス権限(登録)**: **確定(2026-08-29)**。新しい権限区分は設けない。ログイン中の利用者が入力者(事務員)のデフォルトとなり、既存の権限モデル(管理者/一般社員)のまま、一般社員であれば誰でも新規登録できる。
- **アクセス権限(チェック・周知記録)**: チェック状態の更新・周知記録の登録を誰でも行えるか、チェック者・管理者に限定するかは引き続き未確認。
- **担当営業の絞り込み**: **確定(2026-08-29)**。一覧画面に「担当営業」での絞り込み検索を設ける。担当営業は既存の利用者管理(app_user)から選択する想定。
- **得意先マスタ**: **確定(2026-08-29)**。得意先マスタの実体は別サーバー(`10.194.5.55`)にあるが、本アプリのDBサーバー(`10.194.5.57`)側に用意される**ビュー経由で参照する**構成とする。サーバー間の接続(リンクドサーバー等)はDB/インフラ側で吸収済みの前提で、**本アプリからは`10.194.5.57`に対して通常のSELECTを行うだけでよく、`10.194.5.55`の存在を意識する必要はない**。未確認: 参照するビュー名・カラム構成(得意先コード、得意先名、担当営業の紐付け方法等)、ビューが読み取り専用かどうか。
- **既存のスコープ外機能との関係**: 要件定義書では「ワークフロー・承認」は明示的にスコープ外とされている。本機能の「チェック者による確認」はワークフロー的要素を含むため、単純な入力フォーム+一覧に留めるか、簡易な承認機能まで持たせるか要確認。
- **事故区分・選択式項目**: 「送り先間違い」等、事故区分が選択式(プルダウン)になっている可能性が高いが、選択肢の全リストは未確認。
- **正確な項目一覧・レイアウト**: 本ドキュメントの2章は推測を含むため、実際の項目・入力規則(必須/任意、文字数、日付形式等)の確認が必要。
- **既存Excelとの移行**: **不要と確定(2026-08-29)**。過去の事故報告(Excelファイル)は本機能にインポートしない。今後発生する事故報告のみを本機能で扱う。

## 未確認事項

- 正確な項目一覧・入力規則(2章参照)
- チェック・周知記録の操作権限(誰でも可か、チェック者・管理者限定か)
- チェック者による確認をワークフローとして実装するか、単純な状態フラグに留めるか
- 得意先マスタ参照用ビューのビュー名・カラム構成・担当営業との紐付け方法(DB側の準備待ち)

**確定済み(2026-08-29)**:
- 過去のExcelデータの移行は不要。本機能は今後発生する事故報告のみを対象とする。
- アクセス権限(閲覧)は全社員可とする。
- 新規登録に特別な権限は設けない。ログイン中の利用者(一般社員)が入力者のデフォルトとなる。
- 一覧画面に「担当営業」による絞り込み検索を設ける。
- 得意先マスタの実体は別サーバー(10.194.5.55)だが、本アプリのDBサーバー(10.194.5.57)上のビュー経由で参照する。アプリ側はリンクドサーバー構成を意識しない。
- 得意先は既存の得意先マスタから取得する。マスタは本アプリのDBサーバー(10.194.5.57)と同一サーバー上にある。
- 一覧画面に「担当営業」による絞り込み検索を設ける(営業が自分に関連する事故報告を事後的に確認できるようにするため)。
- 新規登録に特別な権限は設けない。ログイン中の利用者(一般社員)が入力者のデフォルトとなる。
