# 開発ガイドライン

作成日: 2026-08-27
参照元: `docs/architecture.md`(技術スタック)、`docs/repository-structure.md`、CLAUDE.md
ステータス: ドラフト(要承認)

---

## 1. コーディング規約

- 言語はTypeScriptを共通言語とする(フロントエンド・バックエンド両方)。`any` 型の使用は原則禁止し、境界(外部API・DB結果)でのみ型ガード・バリデーションを行う。
- コメントは基本的に書かない。書く場合は「なぜそうなっているか」(隠れた制約、仕様上の理由)のみとし、コードを読めばわかる内容(何をしているか)は書かない。CLAUDE.mdの原則に従い、タスク名・修正経緯への言及もコードコメントには含めない。
- 過剰な抽象化を避ける。似た処理が3回未満であれば共通化しない。将来の拡張を見越した抽象化(YAGNI違反)を行わない。
- エラーハンドリングは実際に発生しうるケースにのみ実装する。発生しえないケースへの防御的コードは書かない。
- セキュリティ:
  - 掲示板本文(リッチテキスト)は保存前に必ずサニタイズする(許可タグ・属性を明示的に絞る)。フロントエンド側での表示時にも二重にエスケープ処理を意識する。
  - パスワードはハッシュ化(bcrypt等のソルト付きハッシュ)して保存し、平文・逆変換可能な形式では保存しない。管理画面を含めどの画面でも再表示しない。
  - OAuthトークン(Googleカレンダー連携)は暗号化して保存する。
  - SQLインジェクション対策としてクエリはORM/クエリビルダのパラメータバインディングを用い、文字列結合でSQLを組み立てない。
  - ファイルアップロード機能では、ファイル名・パスのサニタイズとアップロード可能な拡張子・サイズの制限を行う。

## 2. 命名規則

- 変数・関数名は英語のキャメルケース(`camelCase`)、クラス・コンポーネント名はパスカルケース(`PascalCase`)、定数は`UPPER_SNAKE_CASE`とする。
- ドメイン用語(掲示板・カレンダー・会議室予約等)の英語表記は `docs/glossary.md` の対応表に従い、プロジェクト内で表記を統一する(例: 「非表示」→`isHidden`、「公開対象」→`visibility`)。
- DBテーブル名・カラム名はスネークケース(`snake_case`)とし、`functional-design.md` のER図のエンティティ名・属性名をそのまま採用する。
- APIエンドポイントはケバブケース(`kebab-case`)のパスとする(例: `/api/meeting-finder/search`)。
- ファイル名は原則キャメルケースまたはケバブケース(フロントエンドのコンポーネントファイルはパスカルケース `TopPage.tsx` のように、フレームワークの慣習に従う)。

## 3. スタイリング規約

- Tailwind CSSを共通のデザインシステムとして使用し、統一感を保つ(CLAUDE.md規定)。
- モックアップ(`docs/mockups/*.html`)で使用しているデザイントークンをTailwind設定(`tailwind.config`のtheme拡張)に反映する。
  - カラー: indigo(#4F5FAD、主要アクション)、coral(#E2725B、注意・強調)、teal(#3E8E82、完了・成功系)、および各soft版(背景用の淡色)。
  - フォント: Murecho(Google Fonts)。
  - 角丸: カードは14px、ボタン・入力欄は6〜8px。
  - 罫線テーブル: `border-collapse`ではなくグリッド+個別ボーダーで罫線を表現するモックアップの手法を踏襲する(週間ガントチャート等)。
- インラインスタイル(style属性)は原則使用せず、Tailwindユーティリティクラスで表現する。モックアップは確認用HTMLのため`<style>`タグを使用しているが、実装時はTailwindへ置き換える。
- レスポンシブ対応は必須要件ではないが(社内利用中心)、最低限PCブラウザとiPhoneブラウザ(Googleカレンダー連携対象の営業職向け)での表示崩れがないようにする。

## 4. テスト規約

- ユニットテスト: 各バックエンドモジュール(`backend/src/modules/*`)のビジネスロジック(特に会議候補日時抽出のfree/busy計算、権限判定、サニタイズ処理)を対象に必須とする。
- 統合テスト: 認証、掲示板CRUD、ファイルアップロード/ダウンロード、Googleカレンダー同期(モック使用)など、DB・外部APIを含むフローを対象とする。
- セキュリティ関連のテスト(XSSサニタイズ、パスワードハッシュ化、権限チェック)は重点的にカバーする。
- コード変更後は必ずリント・型チェック・テストを実施する(CLAUDE.md規定)。CIでこれらを自動実行し、失敗時はマージしない。
- UIの見た目確認は、可能な場合は実際にブラウザで機能を操作して確認する(自動テストは機能の正しさを保証するが、UI/UXの妥当性は別途目視確認が必要)。

## 5. Git規約

- コミットメッセージは変更の「なぜ」を簡潔に記述する(1〜2文)。
- 破壊的操作(force push、履歴書き換え等)は行わない。
- 機能追加・修正は `.steering/[YYYYMMDD]-[開発タイトル]/` の作業単位に対応させ、関連するコミット・ブランチ名にタイトルを反映させることを推奨する。
- レビュー前にリント・型チェック・テストがすべて通過していることを確認する。
- `storage/`(ファイル実体)や環境変数・秘密情報(OAuthクライアントシークレット、DB接続情報等)はリポジトリにコミットしない(`.gitignore`で除外)。
